# 意思決定ログ：標準のシンプル構成を決める（サービスの名前は書かない）

- 日付：2026-11-22
- 工程：2 企画（プラグインの方針の見直し）
- プラグインの版：0.19.1 → 0.20.0

## 問い

`04-minimal-tech-decisions.md` で「リリースはシンプル構成」と決めたが、中身が未決定だった。そのため、ステップ4で Web を選んだときやステップ7で、AIが技術の選択肢を何度も並べる（Round 5 の R5-13・B9、`simulations/v0.19-check.md` のケースA）。標準の構成をどう決め、どこまでプラグインに書くか。

## 選択肢（AI案）

| 論点 | 案 |
| --- | --- |
| 構成 | 画面とサーバーの処理を1つにまとめたアプリ、自分で管理しなくてよいデータベースと認証、サーバーからのAI呼び出し、決済代行、公開の場所。本人に聞くのは「どこに置くか」と「有料プランにいつ切り替えるか」だけ |
| 1. サービスの名前を書くか | 書く（迷う余地を減らす）／書かない |
| 2. 別の技術を使いたいと言われたら | 理由を意思決定ログに残せば外れてよい |
| 3. 社内ツールをアーティファクトのまま正式導入してよいか | 条件つきで認める（情シスの確認を必須にする） |

## 決定

構成は AI案のとおり。本人の言葉：「1は書かない。2,3はオススメ」

- 1：サービスの名前は書かない。役割と、選ぶときの条件（日本のリージョン、データベースの側で読み書きの決まりを決められる、利用者が自分で解約できる決済画面、など）だけを書き、具体的なサービスはAIが作るときに選んで料金・利用条件を確かめる
- 2：標準から外れたいと言われたら止めず、理由を意思決定ログに残して、その部分だけ外す
- 3：社内ツールで、全員が同じ Claude の組織にいて、データの重さが軽・中で決済がなく、情シスがよいと言ったときだけ、アーティファクトのまま正式に導入してよい

## 根拠と未検証の前提

- 根拠：本人の判断【推測】。無料プランには商用で使えないもの、しばらく使われないと止まるものがある【行動：公開の場所とデータベースの利用条件を調べて確かめた（2026-11-22）】
- 未検証の前提：
  - サービスの名前を書かなくても、AIが条件から毎回同じような構成を選び、選択肢を並べ直さない
  - アーティファクトのまま導入した社内ツールで、持ち主の異動・退職のときに引き継げる

## 見直す条件

- シミュレーションで、ステップ7に入ったAIが技術の選択肢を3つ以上並べた場合（名前を書くかを決め直す）
- アーティファクトのまま導入した社内ツールで、読み書きのきまりの緩みや引き継ぎの失敗が起きた場合
