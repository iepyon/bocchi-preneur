# シミュレーション Round 4（v0.9.0・架空プロジェクトを試作まで通す）

架空の創業者（地方でWeb制作を7年ソロで続けてきたデザイナー出身・非エンジニア寄り）が、「ひとりび」（ソロ同士がゆるくつながるWebアプリ）を、ステップ1から価値検証の基準を記録するところまで進めた。成果物は `samples/hitoribi/`。

## うまく働いたこと
- 【確認】想定インタビュー（R3-1）：5件とも `fieldwork/rehearsal/` に分け、【推測】として扱い、ゲートは閉じなかった。本人が引き受けて進む判断は、意思決定ログに残った。
- 【確認】v0.9.0 のコンテンツの要件：「痕跡は自由記述。見回りを1人で半年続けられるか」と問い詰めた結果、書き置きを定型文だけにし、痕跡は通報で隠す仕組みとセットにした。v0.8.0 までなら、要件は「書き置き機能」の1行で通っていた。
- 【確認】v0.9.0 の層の対応表：ステップ3で「場所ごとの灯の数」を足したくなったとき、先に要件へ戻ってつながりを確かめた（S14 と同じ流れ）。
- 【確認】v0.9.0 の骨格：初回・空・失敗の状態を先に描いたので、試作品で空の画面に迷う箇所がなかった。

## 見つかった課題

### 【R4-1】人が集まって初めて価値が出るプロダクトの扱いがない
```
本人：20人だと、同じ時間に灯がともっている人が少なすぎて、ひとりではない感じが出ないかもしれない
```
ステップ1〜5は、1人のユーザーが1人で価値を感じる道具を前提にしている。ユーザー同士の関わりが価値になるプロダクト（場・マーケットプレイス・コミュニティ）では、価値検証の人数が「判定に足りるか」だけでなく、「価値が出る密度に足りるか」も問題になる。
→ 提案：ステップ2の戦略に「価値が出るのに必要な最小の密度（同時に何人、どの時間帯に）」を加える。ステップ5の着手前に、その密度を検証期間中に作る方法（時間を寄せる、小さな集団に限定する、運営者自身が参加する）を本人に決めてもらう。

### 【R4-2】知らない人同士が書き込むコンテンツの公開準備がない
ステップ9のデータの重さは「預かるデータ」を見るが、利用者同士が書き込むもの（嫌がらせ、宣伝、個人情報の書き込み）への対応方針は問わない。このサンプルでは企画の段階で本人が気づいたが、問いとしては存在しない。
→ 提案：ステップ2のコンテンツの要件に「利用者が書くものがあるなら、困った投稿を誰がどう止めるか」を加える。ステップ9の公開準備に「通報の受け方と、投稿を消す基準」を加える。

### 【R4-3】テストシナリオ表が1人の操作を前提にしている
ステップ4の確認で、2人のユーザーを同時に動かしたときだけ出る不具合が見つかった（一方の画面が古いままで、もう一方の操作と食い違う）。ステップ7のテストシナリオ表は「ユーザーが実際にやりそうな操作」を作らせるが、複数のユーザーが関わる操作の組み合わせには触れていない。
→ 提案：ステップ7（と、ステップ4の確認）で、ユーザー同士が関わる機能があるなら、2人以上を同時に動かすシナリオを最低1本入れる。
