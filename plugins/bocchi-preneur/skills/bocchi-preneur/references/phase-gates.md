# 工程ゲート

目次：一覧／すべての工程に共通する条件／1 調査／2 企画／3 試作／4 検証／5 公開／ゴール：新規事業化まで通しきった

工程の最後のステップを終えたら、次の工程に入る前にこのファイルで工程ゲートを確かめる。

工程ゲートは次の3つでできている。
1. **ステップのゲート**：工程に含まれる各ステップのゲート。中身は各ステップの references にある。ここでは繰り返さない。
2. **工程として確かめること**：ステップをまたいで初めて確かめられること。下の各工程の表。
3. **工程の判断**：その工程で本人が責任を持って決めること。本人の言葉で記録する。

満たしていない条件があれば、`/bocchi-preneur:next` と同じく、その条件を1つ挙げて、埋めるための問いを1つだけ出す。

## 一覧

| 工程 | ステップ | 工程の判断（本人が決める） | 満たせないときの戻り先 |
|---|---|---|---|
| 1 調査 | 1 | 誰のどの課題に賭けるか | ステップ1の冒頭、またはやめる |
| 2 企画 | 2 | 入れるもの・入れないもの、預かるデータ | ステップ2、課題が揺らいだら調査 |
| 3 試作 | 3・4 | この試作で何を確かめるか | ステップ3・4 |
| 4 検証 | 5・6 | 進む・作り直す・やめる、いくらで売るか | 作り直すなら SKILL.md「作り直すと決めたら」、やめるならアーカイブ |
| 5 公開 | 7〜10 | 公開してよいか、どのリスクを受け入れるか | 該当するステップ |

## すべての工程に共通する条件

- [ ] 工程内のステップが、すべて「完了」か「スキップ（理由：本人の言葉）」になっている
- [ ] 「宿題待ち」のステップが残っていない（残っていれば工程ゲートは閉じない。先の工程に進むこと自体は止めない）
- [ ] 工程の判断が、本人の言葉で state.md の「工程の判断」に1行で記録され、`docs/bocchi/decisions/` に意思決定ログがある（SKILL.md ルール12）。根拠に証拠ラベル（推測／発言／行動／コミット）が付き、見直す条件が事実の形で書かれている
- [ ] 工程内でゲートを満たさずに進んだことが、それぞれ意思決定ログにある（意思決定ログ「いつ書くか」5）
- [ ] 読み手への要約 `docs/bocchi/report.md` の冒頭5行が、この工程を通った時点の内容に更新され、本人が自分の言葉に直した（SKILL.md ルール12）
- [ ] 前の工程で決めたことと矛盾していない。矛盾があれば、どちらを直すかを本人が決めた（SKILL.md ルール8）
- [ ] 「説明待ち」のステップが残っていない（本人だけで今すぐ済ませられるので、宿題待ちと違い工程ゲートの前に必ず済ませる。SKILL.md ルール11）

ステップを飛ばした場合も、工程の判断は省略しない。判断できる材料がなければ、「材料が足りないまま進む」と本人が決めたことを、そのまま記録する。

## 1 調査（ステップ1）

**ステップのゲート**：ステップ1（前半と後半）

**工程として確かめること**
- [ ] 撤退基準とタイムボックスが、期限と条件の形で決まっている（以降の工程で照らし合わせる基準になる）
- [ ] 課題の根拠に【行動】以上の証拠がある。チャット内の推測と、AIの想定インタビューは数えない
- [ ] 事業化の印が、観察できる事実の形で決まっている（社内の新規事業で承認者の基準を確かめていなければ【推測】と明記）
- [ ] 社外向けなら、届けるトラックのチェックポイント1（受け皿）を終えたか、やらない理由を記録した

**工程の判断**：誰のどの課題に賭けるか
記録の形：「＿＿な人が、＿＿の場面で、＿＿に困っていて、今は＿＿で対処している」【証拠ラベル】

**満たせないとき**：【行動】で課題を確かめられなかったら、対象か課題を直してステップ1をやり直す。撤退基準に当たったら、やめる判断を本人に聞く（SKILL.md「やめると決めたら」）。

## 2 企画（ステップ2）

**ステップのゲート**：ステップ2

**工程として確かめること**
- [ ] 必須の要件それぞれが、調査で確かめた課題（【行動】）に対応している。推測だけに基づく要件は、そうと明記されている
- [ ] 「今回は入れない」ものが3つ以上ある
- [ ] 層の対応表（UXの5レイヤー）で、戦略 → 要件 → 構造がつながっている。コンテンツの要件に、1人で回せない運営の手間が残っていない（残すなら本人が受け入れた）
- [ ] データの重さが「重」なら、公開工程の対策と法務確認を前倒しすることが state.md に記録されている

**工程の判断**：入れるもの・入れないもの、預かるデータ

**満たせないとき**：ステップ2に戻る。要件を詰める途中で課題そのものが揺らいだら、調査に戻るかを本人に聞く。

## 3 試作（ステップ3・4）

**ステップのゲート**：ステップ3・4

**工程として確かめること**
- [ ] 「この試作で確かめたいこと」が1文で書かれていて、受け入れ条件がそれにつながっている
- [ ] 試作の流れが、企画で決めた「価値を感じる瞬間」まで通る
- [ ] 試作中に足した機能や変えた流れが、企画の成果物（要件・構造・層の対応表）にも反映されている
- [ ] データの重さが「重」なら、本物のデータを使っていない
- [ ] 社外向けなら、届けるトラックのチェックポイント2（公開しながら作る）を決めた

**工程の判断**：この試作で何を確かめるか（検証工程で測る仮説）

**満たせないとき**：ステップ3・4に戻る。作りながら仕様の誤りが分かったら、企画の成果物を先に直す。

## 4 検証（ステップ5・6）

**ステップのゲート**：ステップ5・6

**工程として確かめること**
- [ ] 利用者どうしの関わりが価値なら、判定は最小の密度に届いた期間の結果で行っている（届かなかったなら、その事実と、密度の問題か価値の問題かの本人の見立てが記録されている）
- [ ] 人数・期間・指標・合格基準が、結果を見る前に記録されている。基準を変えた場合は、変更前の基準での判定も残っている
- [ ] 判断が、調査で決めた撤退基準と照らし合わされている
- [ ] 価格が支払いの実績と矛盾していない（実際に払った人がいる価格より下げるなら、理由がある）
- [ ] 社内向けなら、価格の代わりに導入効果の試算と、承認者と承認の見込みがある
- [ ] 社内の新規事業なら、承認者・承認の場と時期・予算額が決まり、事業化の印を照らし直した
- [ ] 社外向けなら、届けるトラックのチェックポイント3（側面の入り口・紹介）を決めた

**工程の判断**：進む・作り直す・やめる。進むなら、いくらで売るか

**満たせないとき**：
- 作り直す：SKILL.md「作り直すと決めたら」に従う。
- やめる：SKILL.md「やめると決めたら」に従う。
- 基準に届かないのに進む：根拠を本人の言葉で記録すれば進んでよい。

## 5 公開（ステップ7〜10）

**ステップのゲート**：ステップ7〜10

**工程として確かめること**
- [ ] 公開前に、受け入れたリスクの一覧を本人が読んだうえで「公開する」と決めた。一覧には、レビューとペネトレーションテストで残した指摘、専門家に確認していないセキュリティと法務の論点、AI原価の上限を含める。セキュリティの専門家の助言を受けていないなら、そのことを一覧の先頭に書く
- [ ] 決済があるなら、検証で決めた価格がそのまま実装されている
- [ ] 層の対応表が表層まで埋まり、戦略から見た目までつながっている
- [ ] 公開後に何かあったときの連絡先と、最初に何をするか（止める、知らせる）が決まっている
- [ ] 社外向けなら、届けるトラックのチェックポイント4（ローンチ）を実施した
- [ ] 社内の新規事業なら、承認者に report.md で報告した（または報告の場の日付が決まっている）

**工程の判断**：公開してよいか、どのリスクを受け入れるか

**満たせないとき**：該当するステップに戻る。致命的な指摘が直せないなら、公開範囲を狭めるか（知り合い限定など）、公開を延ばすかを本人が決める。

## ゴール：新規事業化まで通しきった

公開工程のゲートを満たしたら、SKILL.md「ゴール：新規事業化まで通しきる」に従って、振り返り、ローンチした日と最初の反応の記録、事業化の印に照らした本人の判定（達成・未達。未達なら何を待っていて、待つ・次の一段・やめるのどれにするか）、スコープ外の案内をして止まる。判定が記録されたら完了とする。

計測・運用・継続判断（旧「6 保守」、ステップ11）は、このバージョンではスコープ外。
