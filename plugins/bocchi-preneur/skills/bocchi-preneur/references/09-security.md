# ステップ9 セキュリティと公開準備 🟢（攻撃と修正）／🔴（リスク受容と規約の内容）

## 前提
動くプロダクトと、`docs/bocchi/02-spec.md` のデータの重さ。なければ、データの重さを先に決める（飛ばせない最小限）。

## ⚠ 最初に必ず伝えること（省かない）
セキュリティは、このプラグインの中で最もリスクが高い領域。穴があると、利用者の個人情報やお金が漏れ、損害賠償や信用の失墜につながり、事業そのものが続けられなくなることがある。

**AIのレビューとペネトレーションテストは、専門家の診断の代わりにならない。** AIは見落とすし、見つからなかったことは安全の証明にならない。このステップに入ったら、問いより先に次のことを本人に伝える。
- AIのテストは「最低限の自己点検」であり、公開してよいという保証ではない
- 公開前に、セキュリティの専門家（脆弱性診断の事業者、セキュリティに詳しいエンジニアなど）の助言を受けることを強く勧める
- 特に、個人情報・決済・ログイン（認証）・健康情報・他社のデータを扱うなら、専門家の診断を受けてから公開する

本人が「専門家には頼まない」と決めた場合も止めはしないが、その判断と理由、残るリスクを意思決定ログに残し、`docs/bocchi/report.md` にも書く。AIは「AIが確認したので安全です」「問題ありません」とは言わない。言えるのは「AIのテストでは見つからなかった」までである。

## A. セキュリティ（ペネトレーションテスト）
1. **範囲を本人に確認する。** 攻撃してよいのは、本人が所有・管理する自分のアプリのローカル環境・テスト環境だけ。本番の実ユーザーデータ、外部サービスそのものは対象外。
2. **`pentester` エージェントに攻撃させる。**（＝攻撃者役になって実際に侵入を試すテスト）
3. **突破された所をすべて直し、同じ攻撃で再確認する。**
4. **残ったリスクは本人が判断する**：公開前に直す／公開後に直す／受け入れる。
5. **秘密情報**（APIキー、パスワード）がコードやGitに含まれていないかを必ず確認する。
   - データベースの側で決めた読み書きの決まりが効いているかを、必ず攻撃で確かめる（ほかの利用者のデータ、社内の新規事業ならほかの会社のデータを取りに行き、断られること）。画面で隠しているだけになっていないかを見る。アーティファクトのまま導入したなら、ふつうの参加者の立場で記録を読んで確かめる
6. **専門家の助言を受けるかを本人に決めてもらう。** データの重さが「重」、または決済・ログインがあるなら、専門家の診断が済むまで公開工程のゲートを閉じない（受けずに公開すると本人が決めたなら、上の「最初に必ず伝えること」のとおり記録する）。

## B. 公開準備（社外向けは必須）
AIは下書きを作れるが、**法的な助言はできない**。本人の事業内容に合っているかを本人が確認し、課金や重いデータを扱うなら専門家（弁護士・行政書士など）の確認を勧める。

- **利用規約**：禁止事項、免責、AIの出力の扱い、解約・返金の条件
- **プライバシーポリシー**：何のデータを、何のために、どこに（AI事業者への送信を含む）、どれくらい保存するか
- **特定商取引法に基づく表記**（日本で有料で売る場合）：事業者名、連絡先、価格、支払い時期・方法、返品・解約の条件など
- **海外に売る場合**：GDPR（欧州）など、売る地域のルールがあることを伝え、専門家への確認を勧める
- **サポートの窓口**：問い合わせ先、返信の目安
- **返金・解約の流れ**：ユーザーが自分で解約できること
- **利用者の書き込みがほかの人に見えるなら**：通報の受け方（どこから、誰に届くか）、投稿を隠す・消す基準（禁止事項と対応させる）、対応までの目安。ステップ2で決めた止め方が、実装と規約の両方に入っているかを確かめる

社内向けの場合：社内の情報セキュリティ規程、扱うデータの持ち出し可否、承認フローを本人に確認する。
