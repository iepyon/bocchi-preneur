# ステップ7 本番実装 🟢

## 前提
価値検証で「進む」と判断した記録（`docs/bocchi/05-value-test.md`）と、決めた価格（`docs/bocchi/06-pricing.md`。課金を実装するため）。なければ、進むと判断した根拠と価格（社内向けなら承認の見込み、社内の新規事業なら予算と承認の見込み）を本人に聞き、記録してから始める。

**入る条件（省けない）**：ステップ5のゲートを、本物の結果（想定ではない利用者の行動とコミット）で満たしていること（SKILL.md ルール14）。満たしていなければ、このステップには入らず、「外に出る（本物に試してもらう相手と日付を決める）」か「やめる」を示す。本人が押し切ろうとしても入らない。

## 目的
価値検証を通ったものを、実際に人に使ってもらえる品質で作る。

## 進め方の原則
- **作るAIと、確かめるAIを分ける。** 実装した本人（AI）は自分の間違いに気づきにくい。実装が一区切りつくたびに `strict-reviewer` エージェントに厳しくレビューさせる。codex CLI が入っていれば、別系統のAIにも見せるとさらに見落としが減る（`/bocchi-preneur:review` を参照）。
- **大きな作業は分ける。** 全体計画を立てる役と、個々の実装をする役（サブエージェント）に分け、並列で進めてから取りまとめる。
- **課金・決済のテストもAIに任せる。** Stripe などのテスト用カード番号を使い、決済が通るかをAIに確かめさせる。本番のカード情報は絶対に使わない。
- **最後の確認は人がする。** その手前の検証はAIに一通りやらせ、本人が触るのは仕上がったものだけにする。

## 着手前に本人に決めてもらうこと
冒頭の問い：「リリースの時点で、ユーザーができなければいけないことは何ですか。試作品から増やすもの・削るものを教えてください。」

- リリース時点の受け入れ条件を本人の言葉で記録する。
- 「あれもこれも」になったら、ステップ2で決めた「今回入れない」リストを見せて問い詰める。

## 標準のシンプル構成
本番は、次の構成を標準とする。技術の選択肢を並べない。具体的なサービスは、下の条件を満たすものをAIが1つずつ選んで示し、選んだ理由と料金・利用条件を作るときに確かめて伝える。

| 役割 | 標準 | 選ぶときの条件 |
|---|---|---|
| 画面とサーバーの処理 | 両方を1つにまとめられるWebの枠組みで、アプリを1つだけ作る | 広く使われていて、AIが作り慣れている |
| データの保存 | 自分で管理しなくてよいデータベース | 日本のリージョンを選べる。誰が何を読み書きできるかを、データベースの側で決められる |
| ログイン | データベースと同じサービスの認証 | メールに届くリンクで入れる。社内向けなら会社のアカウントで入れる |
| AI（使うときだけ） | サーバーからAIを呼び出す | 鍵はサーバーにだけ置く。下の「AI原価のガードレール」を付ける |
| 同時にいる人とのやりとり（要るときだけ） | データベースと同じサービスのリアルタイムの機能 | 新しいサービスを足さずに済む |
| メールの送信（要るときだけ） | メール送信のサービス | 自分のドメインから送れる |
| 決済（有料のときだけ） | 決済代行 | 支払いのページと、利用者が自分で解約できる画面を決済代行の側で用意できる。カード情報は自分で持たない |
| 公開する場所 | 自分でサーバーを管理しなくてよい公開の場所 | 枠組みと相性がよい |

### 本人に決めてもらうのは2つだけ
1. **どこに置くか**：社外向けは、上の構成のまま。社内向け・社内の新規事業は、社外のサービスに社内のデータを置いてよいかを、先に情シスに確かめる宿題にする（チャットの中では分からない）。置いてよければ上の構成のまま、ログインを会社のアカウントにする。会社のクラウドに置く決まりがあれば、アプリの形は変えずに、置き場所とログインを会社のものに替える。
2. **有料プランにいつ切り替えるか**：公開の場所やデータベースの無料プランには、商用で使えないもの、しばらく使われないと止まるものがある。手元での確認や短い試作は無料プランでよいが、利用者に渡す時点で有料プランにするのを標準とする。月々の費用はステップ6の試算と照らし合わせる。

### 標準から外れたいと言われたら
止めない。外れる理由（使い慣れている、会社の基盤がある、など）と、外れて失うもの（AIの作り慣れ、手順の案内が薄くなる、など）を1行ずつ示し、本人の理由を意思決定ログに残してから進む。外れるのは言われた部分だけにし、ほかは標準のままにする。

## 試作品をアーティファクトで作った場合
アーティファクトは一般公開や決済に向かないので、ここで Web（上の標準のシンプル構成）に作り直す。

ただし、**社内ツールで次をすべて満たすなら、アーティファクトのまま正式に導入してよい**（例外）。どちらにするかは本人が決め、意思決定ログに残す。
- 使う人が全員、同じ Claude の組織（Team・Enterprise）にいる
- データの重さが軽か中で、決済がない
- 情シスに、アーティファクトに社内のデータを置いてよいかを確かめ、よいと言われた（確認は省けない。記録の読み書きのきまりは鍵ではなく、持ち主と編集者（ページを公開し直せる人）が後から緩められることも伝えて確かめる。使う人は編集者ではなく参加者として共有し、編集者は持ち主のほかに最小限にする）

アーティファクトのまま導入するときは、作り直しの代わりに次を行う。
- 試作品を、リリース時点の受け入れ条件に合わせて直す。このステップの進め方の原則（作るAIと確かめるAIを分ける、など）とゲートはそのまま当てはめる
- AIの費用は使う人それぞれの利用枠から出るので、月額の上限の代わりに、1人あたりの利用上限が効いていることを確かめる
- 記録の読み書きのきまりが効いているかを、ふつうの参加者の立場で記録を読んで確かめる（見えてはいけない記録が見えないか）
- 持ち主が異動・退職したときに、誰がアーティファクトを引き継ぐかを本人に決めてもらう

作り直すときは、次のとおり。
- 試作品で使った機能を、Web の部品に置き換える。AIが対応を表にして本人に示す。
  - 記録が残る → データベース
  - 誰が使ったか分かる → ログイン（認証）
  - 今いる人とやりとりできる → リアルタイムの通信
  - AIと話せる → サーバーからのAIの呼び出し。鍵はサーバーにだけ置き、下の「AI原価のガードレール」を付ける。試作品では使う人の利用枠だったAIの費用が、ここから作る人の原価になることを本人に伝える
- 試作品の記録（価値検証の結果を含む）は捨てない。AIが書き出して `docs/bocchi/fieldwork/` に残し、本番に引き継ぐかは本人が決める。引き継ぐなら、利用者に知らせてから移す。
- 試作品のアーティファクトは、価値検証の証拠として消さずに残す。

## AI原価のガードレール（AIを使うサービスは必須）
- ステップ2で仮決めした1ユーザーあたりの利用上限を実装する。
- 1ユーザー・1日あたりの上限、全体の月額上限（超えたら通知・停止）を設ける。
- AIの呼び出しが失敗したときの表示と再試行を実装する。

## AIチャットのように操作が無限にあるサービスの場合
すべてのパターンを試すことはできない。代わりに、
1. AIに「ユーザーが実際にやりそうな操作」のテストシナリオ表を作らせる。
2. 本人に「この範囲で使われると考えてよいか」を確認する（ここは本人の判断）。
3. シナリオ表をすべてAIに実行させ、結果を記録する。

## 利用者どうしが関わる機能がある場合
1人で触るだけでは出ない不具合がある（一方の画面が古いままで、もう一方の操作と食い違う、など）。テストシナリオ表に、**2人以上を同時に動かすシナリオを最低1本**入れる（例：Aが投稿 → Bに表示される → Bが反応 → Aに届く）。ブラウザを2つ同時に動かす自動テストをAIに書かせて実行させる。

## 根深いバグが出たら
表面的な修正は別の問題を生むことが多い。`root-cause-analyst` エージェントに根本原因を分析させ、直し方の案を平易に並べさせる（まだ実装しない）。本人に「どの案で行くか」を選んでもらってから直す。本人が選べないときは、各案の「失うもの」を言い換えてもう一度示す。
