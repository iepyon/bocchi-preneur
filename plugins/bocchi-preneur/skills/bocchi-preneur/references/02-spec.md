# ステップ2 仕様設計（UXの5レイヤー下3層＋データの重さ）

## 前提
`docs/bocchi/01-concept.md` の「対象ユーザー」「課題」「最初の一段」。なければ、この3つを3問で埋めてから始める。

## 前提知識：UXの5レイヤー
UXデザインで広く使われる、ユーザー体験を5つの層に分ける考え方。下から 戦略 → 要件 → 構造 → 骨格（ステップ3）→ 表層（ステップ8）。上の層は下の層と矛盾してはいけない。このステップでは下3層を1層ずつ固める。各層で決めることと、層をまたぐ確かめ方は UXの5レイヤー（SKILL.md の工程表で、このステップと一緒に読むもの）にある。

層ごとに、AIが「その層の文書に普通入る項目」を枠として出し、本人と1項目ずつ埋める（UXの5レイヤー「AIの使い方」）。

## 層ごとの役割分担
- 戦略 🔴：ユーザーのニーズ、事業としての目的、**成功の指標**を本人の言葉で埋める。成功の指標は「何が起きたら、この戦略が当たったと言えるか」。数字は仮でよく、ステップ5の価値検証と、ステップ10のローンチ後の最初の反応で照らし合わせる。ステップ1で決めた事業化の印と食い違わないようにする。
  - **利用者どうしの関わりが価値になるプロダクト**（場・マーケットプレイス・コミュニティ・相談の場など）なら、**価値が出るのに必要な最小の密度**も決める。「同時に何人、どの時間帯にいれば、価値を感じられるか」。数字は仮でよく、ステップ5で、検証期間中にその密度を作る方法を決める
- 要件 🔴：入れる・入れないは本人が決める。AIは漏れと矛盾を指摘する。要件は2種類に分けて書く。
  - **機能の仕様**：各機能が何をするか、何をしないかを1〜2行で
  - **コンテンツの要件**：各機能に要る文章・画像・データ。誰が用意し、どれくらいの頻度で更新するか（「ユーザーが書く」「本人が毎週書く」「最初に一度だけAIが作る」など）。運営に手がかかるコンテンツは、1人で回せるかを本人に確かめる
    - **利用者が書いたものがほかの人に見えるなら**、困った書き込み（嫌がらせ、宣伝、個人情報や社外秘の書き込み）を誰がどう止めるかも決める。例：定型文だけにする、公開前に運営者が読む、通報で隠して週1回見回る、時間が来たら消す。どれも1人で続けられるかを確かめる
- 構造 🟡：AIが案を作り、本人が「その人は本当にこの順で使うか」を確かめる。構造は2つに分けて書く。
  - **情報の構造**：画面と情報の分類・階層、呼び名。呼び名はインタビューで相手が使っていた言葉を優先する
  - **操作の設計**：主要な操作ごとに、システムがどう応えるか、失敗したとき・取り消したいときどうなるか。初回（まだ何もない状態）に何を見せるか
- **データの重さ 🔴**：何を預かるかは本人が決める。AIは重さの分類と、それに伴う義務を平易に示す

## データの重さ（必ずここで決める）
扱うデータを3段階に分類し、本人に確認する。
- 軽：メールアドレス、表示名、利用ログ
- 中：氏名・住所・電話、決済情報（決済代行に任せ、自分では持たない設計が原則）、業務データ
- 重：マイナンバー、健康・医療、財務の詳細、子どもの情報、位置情報の履歴

「重」を扱う場合は、本当に最初の版で必要かを問い詰める。必要なら、ステップ9の対策と法務確認を前倒しにすることを state.md に記録する。法令上の扱いはAIが断定せず、専門家への確認を勧める。

## AI原価の上限
裏でAIが動くなら、1ユーザーあたりの利用上限（回数・量）をここで仮決めする。上限がないと、少数のヘビーユーザーで赤字になる。数字は本人が決め、ステップ6で見直す。

## ゲート
- [ ] 戦略：ターゲット、ニーズ、提供価値、事業としての目的、成功の指標が本人の言葉で書かれている。利用者どうしの関わりが価値なら、最小の密度の仮決めがある
- [ ] 要件：優先度順の機能の仕様と「今回は入れない」もの。各機能のコンテンツの要件（誰が用意し、どれくらいの頻度で更新するか）がある。利用者の書き込みがほかの人に見えるなら、困った書き込みを止める方法が決まっている
- [ ] 構造：情報の構造（画面と情報の分類・呼び名）と、初回利用から「価値を感じる瞬間」までの流れが1本以上ある。主要な操作に、失敗したとき・取り消したいときのふるまいがある
- [ ] 層の対応表（UXの5レイヤー）の戦略・要件・構造の列が埋まり、戦略につながらない要件がない（あれば「戦略にない」と明記されている）
- [ ] データの重さが分類され、本人が確認した
- [ ] AIを使うなら、1ユーザーあたりの利用上限の仮決めがある
- [ ] 説明チェックが済んでいる（SKILL.md ルール11）

## 冒頭の問い
「ユーザーがこのプロダクトを使い終わったとき、何が変わっていてほしいですか。」

## 問い詰め在庫
- **目的とニーズの区別**：「それはユーザーの望みですか、あなたの事業の望みですか」
- **入れない機能**：「今回あえて入れない機能を3つ挙げてください」
- **戦略との対応**：要件ごとに「これは戦略のどの部分のためですか」
- **価値を感じる瞬間**：「初めて『これいい』と思うのは、使い始めて何分後、どの操作の後ですか」
- **データの必要性**：「そのデータがないと、最初の版は成り立ちませんか」
- **課題検証との照合**：インタビューで出た【行動】と、この流れは合っているか
- **成功の指標**：「この戦略が当たったかどうかは、何が起きたら分かりますか」。「使われたら」なら、誰が、どれくらいの頻度で、をもう一段聞く
- **最小の密度**：利用者どうしの関わりが価値なら、「その人が開いたとき、ほかに何人いれば『いい』と感じますか。それは何時ごろですか」
- **困った書き込み**：利用者が書いたものがほかの人に見えるなら、「困った書き込みが出たら、誰が、どう止めますか。それを1人で続けられますか」
- **コンテンツの手間**：「この機能の中身は誰が、どれくらいの頻度で用意しますか。それを1人で半年続けられますか」
- **失敗したとき**：「この操作がうまくいかなかったとき、その人には何が見えていればいいですか」
- **呼び名**：「この呼び名は、相手が使っていた言葉ですか」

## 成果物 `docs/bocchi/02-spec.md`
戦略（成功の指標を含む）／要件（機能の仕様・コンテンツの要件・入れないもの）／構造（情報の構造、利用の流れのMermaid図、操作の設計）／データの重さ／AI利用上限／層の対応表。
