# 企画書（proposal.md）

これまでの記録を、本人以外の人が通して読める企画書にまとめ直す。社内の新規事業の起案、承認者への提案、出資者・共同創業者・相談相手への説明、社内外のコンテストへの応募などに使う。

置き場所：`docs/bocchi/proposal.md`。雛形は `templates/proposal.md`。

## 読み手への要約との違い
- **読み手への要約**（`docs/bocchi/report.md`）は、工程を通るたびに更新する5分の要約で、「今どこ・何がほしいか」を伝える。
- **企画書**は、本人が求めたときに作る。課題・対象・解決策・競合・ビジネスモデル・検証計画・リスクを、通して読める形にする。
- 企画書はゲートではない。作っても工程は進まず、作らなくても進める。

## いつ作るか
- 本人が求めたとき（`/bocchi-preneur:proposal`）。どのステップの途中でもよい。
- 早い段階で作ってよい。決まっていない節は空のままにせず、「未決定」として論点を並べる（下の「書き方の決まり」）。
- 作ったあとに工程が進んだら、本人が求めたときに作り直す。前の版は Git の履歴に残るので、冒頭の日付だけを新しくする。

## 作る前に聞くこと（1回にまとめて選択式）
- **読み手**：社内の新規事業なら承認者を初期値にする。ほかに出資者・共同創業者・相談相手・コンテストの審査員・未来の自分。本人が決める。
- **市場と競合の机上調査をするか**：する（公開情報を調べ、出典つきで載せる）／しない（本人の記録だけでまとめる）。する場合は、Web を調べてよいかもここで確かめる。

## 節と、どの記録から書くか
雛形の節の順に書く。元の記録がない節は、その節の「未決定の論点」だけを置く。

| 節 | 主な元の記録 |
|---|---|
| エグゼクティブサマリー | 下の節すべて（最後に書く） |
| 背景と課題 | `docs/bocchi/01-concept.md`、`docs/bocchi/fieldwork/` |
| ターゲットと市場 | `docs/bocchi/01-concept.md`、`docs/bocchi/decisions/`、机上調査 |
| プロダクトコンセプトと提供価値 | `docs/bocchi/01-concept.md`、`docs/bocchi/02-spec.md` |
| 機能構成とMVP範囲 | `docs/bocchi/02-spec.md`（なければ `docs/bocchi/01-concept.md` の最初の一段） |
| 競合・代替手段と差別化 | `docs/bocchi/01-concept.md`（本人が挙げた今の代替手段）、机上調査 |
| ビジネスモデル | `docs/bocchi/06-pricing.md`、state.md の「事業化の印」 |
| 検証計画 | state.md の撤退基準、`docs/bocchi/05-value-test.md`、出している宿題 |
| ロードマップ | state.md の時間・タイムボックス、工程の状態 |
| リスクと対策 | `docs/bocchi/02-spec.md` のデータの重さ、`docs/bocchi/09-security.md`、`docs/bocchi/decisions/` |
| 未検証の前提と次のアクション | 【推測】【発言】のまま残っている前提、出している宿題、state.md の「次に決めること」 |
| 読み手にお願いしたいこと | `docs/bocchi/report.md` の「何がほしいか」 |

読むのは state.md と、表の記録のうち実在するものだけ。全部を先に読まない。

## 書き方の決まり
1. **本人が決めたことと、AIが調べたこと・考えたことを分ける。** 事業判断（対象、課題、解決策、価格、払う人、撤退基準、事業化の印）は、本人が決めたものだけを書く。本人の発言は「」で、AIの要約は「要約：」を付ける。
2. **本人が決めていない事業判断は、代わりに書かない。** その節には「（未決定）」と見出しに付け、決めるための論点を表で並べる。選択肢を出すなら「AI案」と書き、どのステップで決めるかを添える。
3. **証拠ラベルを付ける。** 元の記録のラベル（【推測】【発言】【行動】【コミット】）をそのまま引き継ぎ、強く書き換えない。
4. **机上調査は、すべて【推測】として扱い、出典を付ける。** 数字には出典のURLを付け、調査会社によって数字が大きく違うときはそう書く。本人の課題が確かめられたかのように書かない。
5. **想定インタビューの結果は、証拠に数えない。** 想定で代用中の宿題があれば、「未検証の前提と次のアクション」に、本物に聞く相手と期限とあわせて書く。
6. **本人が約束していないことは書かない。** 予定・約束・数値目標を下書きに足したくなったら、本人に聞く。
7. **冒頭に、作った日と、何をまとめたものかを書く。** どのステップまでの記録と、机上調査をしたかどうか。読み手は、どこまでが確かめたことかを冒頭で知る。
8. **元の記録へのリンクを置く。** 判断には `docs/bocchi/decisions/` の該当ファイルを、数字には元の記録を添える。
9. **数字や比較は表にする。** 利用の流れなど、図があると伝わるものは Mermaid で描いてよい。

## 作ったあと
1. 本人に読んでもらい、自分の言葉に直してもらう。少なくとも、エグゼクティブサマリーの「課題」と「解決策」、最後の「読み手にお願いしたいこと」は本人の言葉にする（説明チェックの代わりに、本人の言い直しを求める）。直してもらうための問いは、1問ずつ出す。
2. 下書きの中で、元の記録と食い違うところ（AIのまとめ直しで意味が変わったところ）を本人が見つけたら、企画書ではなく元の記録を正として直す。元の記録の方を直すと本人が決めたら、元の記録を直し、state.md の変更履歴に1行残す。
3. 書き出したら、未決定の節の数と、本人の言葉に直してもらった節を1行ずつ伝えて止まる。工程は進めない。
4. Word・スライド・PDF など別の形式を本人が求めたら、`docs/bocchi/proposal.md` を元に変換する。中身は Markdown の版を正とする。
