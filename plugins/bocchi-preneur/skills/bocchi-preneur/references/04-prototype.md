# ステップ4 プロトタイプ実装 🟢

## 前提
`docs/bocchi/01-concept.md`（対象・課題・最初の一段）、`docs/bocchi/02-spec.md`（流れ・データの重さ）、`docs/bocchi/03-wireframe.md`。欠けていれば、SKILL.md のルール9に従い、最小限を数問で埋める。ワイヤーフレームがなければ、AIが1案だけ作って本人に確認してから実装する。

## 目的
デザインを作り込む前に、一通り動くものを作り、価値検証（ステップ5）に回せる状態にする。

## 最重要ルール：最初は Claude のアーティファクトで「動くアプリ」として作る。だめなら Web
スマホアプリが最終目標でも、最初はスマホアプリにしない。確認のたびにビルドして端末に入れる手間がかかり、試行錯誤が遅くなる。

まず勧めるのは、Claude のアーティファクト（claude.ai 上で動くアプリ）。サーバーが要らず、リンクを渡すだけで試してもらえる。見た目だけのモックで終わらせず、価値を感じる瞬間（ステップ2の戦略）に要るところは、アーティファクトの機能で実際に動かす。試作品の役目は、利用者の【行動】と【コミット】を記録として残すこと（ステップ5で使う）。

アーティファクトで作れないとき（下の「確かめること」の1か2が「いいえ」）は、Web（自分で動かすサーバー）で作る。Web で作ったものは、ネイティブアプリにもAIが翻訳できるので無駄にならない。本人が「最初からアプリで作りたい」と言ったら、この理由を伝えたうえで本人に決めてもらう。

### 確かめること（選ぶ前に、選択式でまとめて聞く）
1. **検証に参加する人は、Claude を使っていますか（使ってもらえますか）。** 試作品の中のAIは、使う人自身の Claude の利用枠を使う。最初に使うとき、許可を求める画面が出る
2. **参加する人は、記録を書き込める立場で招けますか。** 書き込めるのは、持ち主、Team・Enterprise プランで同じ組織の人（閲覧だけの設定を除く）、共有のメニューからメールで「編集者」として招いた人。それ以外の人は読むだけで、ログインしていない人はデータに触れない
   - 社内向けで、組織が Team・Enterprise なら、同僚はそのまま書き込める
   - 社外の人は、メールで編集者として招く。編集者はページを公開し直すこともできるので、相手は少人数の信頼できる人に限り、そのことを本人に伝える
3. **検証で、本物のお金を受け取りますか、または不特定の人に公開しますか。** どちらかなら、その部分（事前予約・先行課金のページなど）は Web で作る。面談で見せる試作品はアーティファクトのままでよい

すべて「はい」（3は「いいえ」）ならアーティファクトで作る。1か2が「いいえ」なら Web で作る。Web を勧めるときは、面談で本人が画面を見せて操作してもらうだけのデモならアーティファクトでもよいこと（その場合、継続利用はアーティファクトでは測れない）を、必ず1行添える。判断は本人がし、理由を一言もらって意思決定ログに残す。

### 機能の選び方（アーティファクトで作るとき）
本人には機能の名前ではなく「本人に伝える言い方」で示す。どの機能を使うかは、AIがステップ2の要件から選び、どの要件のためかを添えて本人に確かめる。機能の名前や中身は変わることがあるので、作るときにアーティファクトの機能の最新の説明を確かめる。

| 機能 | 本人に伝える言い方 | 使うとき |
|---|---|---|
| `db` | 使った記録が残る | 原則いつも。利用の記録、回答、事前予約の意思などを残す。Claude が後から直接読んで集計できる |
| `user` | 誰が使ったか分かる | 原則いつも。1人ずつ数える（何人が何日使ったか）。記録には名前ではなく識別子だけを残す |
| `sample` | AIと話せる | AIが価値の中心のとき。呼び出した回数を `db` に残し、1人あたりのAI利用量をステップ6の試算に使う |
| `room` | 今いる人とやりとりできる | 利用者どうしが同じ時間にいることが価値のとき。何も残らないので、同時にいた人数などは `db` に残す |
| `comments`（書き込む入口だけ） | 画面に感想を書き込める | 価値検証の面談で、画面の上に感想を残してもらうとき。証拠としては【発言】 |
| `mcp` | いつもの道具（カレンダー、Slack など）のデータを使う | 社内ツールで、利用者本人のデータで試すとき。データの重さを先に確かめ、読むだけにし、なくても動くように作る |
| `assets` | 写真や書類を上げられる | アップロードが利用の流れに入っているとき |
| `dictation`・`tts` | 声で入力する・読み上げる | 声で使うこと自体が仮説のときだけ |

画面ごと保存し直す機能（`artifact`）とプロジェクトのファイルを読む機能（`files`）は、試作では使わない。公開し直せるのが編集者だけで、多くの人に試してもらう検証に向かないため。

アーティファクトで価値検証まで進んだら、公開工程（ステップ7）で Web 版に作り直す（アーティファクトは一般公開や決済に向かない）。そのときは試作品の記録を引き継ぐ。

## AIがやること
- `docs/bocchi/01-concept.md`、`docs/bocchi/02-spec.md`、`docs/bocchi/03-wireframe.md` を読み、一気に試作品を作る。
- 技術選定が必要なら、2〜3案を「何が嬉しく何を失うか」で平易に示し、本人に選んでもらう。
- アーティファクトで作る場合は、次も行う。
  - 記録の読み書きのきまり（誰が読めて、誰が書けて、持ち主が直したり消したりできるか）を本人に平易に示して決めてもらう。初期は「全員が読めて、各自が自分の分だけ書く」か「自分の分は自分しか読めない」。きまりは鍵ではない（持ち主や編集者は後からきまりを緩められる）ことも伝える
  - 参加者にも、試してもらう前に、持ち主（本人）や編集者が何を読めるか（例：各自の規程や相談の中身まで読めるか、利用の回数と日付だけか）を伝える文面を用意する
  - 秘密の情報（APIの鍵など）は試作品に入れない
  - AIを使うなら、ステップ2で仮決めした利用上限を回数として数えて止める。許可されなかったとき・混んでいるとき・利用枠を使い切ったときの画面も、骨格の「失敗の状態」として作る
  - 記録がまだないとき（初回・空）でも画面が動くようにする。見本のデータは試作品に書き込まず、公開したあとにAIが記録として入れる
  - 公開したら、AIが記録の中身を一度読み、書いた記録が残っていること、ほかの人に見せないはずの記録が見えないことを確かめる
- データの重さが「重」なら、試作品では本物のデータを使わず、ダミーデータで作る。
- 骨格（ステップ3）で描いた初回・空・失敗の状態も実装する。表層（色や装飾）は作り込まない。
- 利用者どうしが関わる機能があるなら、完成の前に2人分を同時に動かして確かめる（例：Aが投稿 → Bに表示される → Bが反応 → Aに届く）。1人で触るだけでは出ない不具合（一方の画面が古いままで、もう一方の操作と食い違う、など）がある。
- 作りながら仕様の誤りや漏れが分かったら、コードより先に `docs/bocchi/02-spec.md` と層の対応表を直し、本人に確かめる。
- 完成したら、本人が自分で触れる手順（どのURLを開けばいいか）を1つずつ案内する。アーティファクトなら、参加者への共有のしかた（誰をどの立場で招くか）も案内する。
