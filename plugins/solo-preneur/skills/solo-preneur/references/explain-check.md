# 説明チェック

AIが作ったものを受け入れる前に、本人が自分の言葉で説明する。AIを使うほど学べなくなる（作業を渡すほど、AIの誤りを見抜く力が育たない）ことへの対策で、このプラグインの中心にある約束の1つ。

「動いた」「よさそう」「A でいい」だけで受け入れない。受け入れたものの責任は本人が負う。説明できないものは、責任を負えない。

## いつ行うか

AIが作ったもの、またはAIが下書きして本人が選んだものを、ステップのゲートで受け入れるとき。

| ステップ | 説明してもらうもの |
|---|---|
| 2 仕様設計 | AIが下書きした要件・構造・データの重さ（本人の言葉で書いた戦略は対象外） |
| 3 画面設計 | 選んだ骨格 |
| 4 プロトタイプ | 試作品 |
| 6 価格設計 | AIが作った試算表（社内なら効果の試算） |
| 7 本番実装 | 本番のしくみ（strict-reviewer が残した指摘を含む） |
| 9 セキュリティと公開準備 | 攻撃テストの結果と、残したリスク。規約などの文書 |
| 10 ローンチ | 素材と、ローンチ計画 |

ステップ1と5は、もともと本人の言葉でしか埋めない（🔴）ので、ここでは行わない。ただしステップ5で、AIが結果を集計・整理したものは、その読み方を本人に言ってもらう（`05-value-test.md` の結果が出たあとの問い詰め在庫）。

## 何を言ってもらうか

1. **要点**：これは何をするもので、ステップ2で決めたどのニーズ・どの要件のためにあるか（1〜2文）
2. **弱点**：これで一番起きそうな失敗、または確かめられていないことを1つ
3. 公開工程（ステップ7・9・10）では、さらに：**その弱点を直すか、受け入れるか**。受け入れるなら、外れたときに誰がどう困るか

## 進め方

- 冒頭の問い：「受け入れる前に、あなたの言葉で2つ教えてください。これは何のためのものですか。これで一番起きそうな失敗は何ですか。」
- 自由記述なので、1ターンに1問ずつ（SKILL.md ルール3）。
- **AIは答えを言わない。** 本人が詰まったら、次の順で足場をかける（SKILL.md ルール1と同じ考え方）。
  1. 見る場所を示す（「試作品の最初の画面で、利用者が最初に押すのはどこですか」「試算表のどの数字がいちばん動きそうですか」）
  2. 問いを狭める（「この画面で、データが0件のときはどうなりますか」）
  3. それでも出なければ、本人がこれまでに言ったこと（受け入れ条件、気にしていたこと、インタビューの記録）から弱点の候補を2〜3個並べ、どれが一番起きそうかを理由つきで本人に選んでもらう（SKILL.md ルール1と同じく、候補は本人の発言に由来するものに限る）
- 本人の説明が成果物と食い違っていたら、そこを1つ指摘する。食い違いは、本人の理解の問題か、成果物の誤りかのどちらか。本人に、どちらを直すかを決めてもらう。
- 本人の説明で、成果物の誤りや抜けが見つかったら、受け入れる前に直す。
- AIが書いた文を本人が読み上げる・写すのは、説明として数えない。言い換えてもらう。

## 急いでいるとき・飛ばしたいとき

- 「まとめて進めて」と言われたら、選択式の問いはまとめてよい。ただし説明チェックは省かない。要点と弱点の2問だけにして、短く済ませる。
- 本人が「説明はいいから次」と言ったら、止めない。飛ばすと何が起きやすいか（部長や顧客に聞かれて答えられない、AIの誤りに気づけない）を1行で伝える。そのうえで、ステップの状態を「説明待ち」にして先に進む。ゲートは閉じない（宿題待ちと同じ扱い）。
- 「説明待ち」は、毎回の再開と `/solo-preneur:status` で示し、工程ゲートの前に必ず済ませてもらう。

## 記録

各ステップの成果物（`docs/solo/NN-*.md`）の末尾に「本人の説明」として残す。

```
## 本人の説明（YYYY-MM-DD）
- 要点：「本人の言葉」
- 弱点：「本人の言葉」
- 直すか受け入れるか（公開工程のみ）：「本人の言葉」
- 説明で見つかって直したこと：（あれば。AIの要約には「要約：」を付ける）
```

飛ばした場合は「本人の説明：未（説明待ち。理由：本人の言葉）」と書き、state.md のステップの状態も「説明待ち」にする。
